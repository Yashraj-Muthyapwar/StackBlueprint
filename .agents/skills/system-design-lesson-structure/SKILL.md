# System Design Lesson Structure

Use this skill to create or revamp a lesson in the System Design track. The reference implementation is **Functional vs Non-Functional Requirements**:

- Lesson content: `functionalVsNonFunctional` in `src/lessons/system-design/foundations-content.ts`
- Lesson-owned animation: `src/components/system-design/foundations/UrlShortenerWhiteboard.tsx`
- Global whiteboard: `src/components/lesson/diagram-board/` (see section 5)
- Renderer: `src/components/system-design/SectionRenderer.tsx`

**The rule:** the *frame and controls* are shared so every lesson has the same UI and UX; what is *drawn inside* (the animation scene, the whiteboard boards) belongs to the lesson. One running example is used for the whole lesson (the reference lesson uses a URL shortener) so concepts connect without changing examples.

## 0. Choose the mode

- **Create**: the lesson does not exist. Add it to the right topic module, register it (section 1.2), build its animation, exercises, whiteboard board, takeaways and quiz together.
- **Revamp**: keep its `slug`, route, position and progress id. Replace content, then delete what the old version no longer uses (old animations, section kinds, helper files) after confirming nothing else imports them. This folder may not be a git repository: copy anything you delete to a backup first and say where.

### Content fidelity

- When the user supplies lesson text, **use it verbatim**. Only add structure (section markers, components, order). Do not reword, trim, reorder facts or "improve" it. If supplied text has a heading such as `4. EXAMPLE — Design a URL shortener`, split it into a marker (`4 · Example`) and a heading (`Design a URL shortener`). That is structure, not a content change.
- Text the user did not write (animation narration, exercise feedback, takeaways, quiz) must be original, specific and free of filler. No AI slop, no padding, no generic claims.
- **Never write em dashes** in lesson text, UI strings or narration. Use a colon, comma or full stop.
- Refer to other lessons by name or as "the previous lesson", never "Lesson 1" or "Module 2".
- Do not copy third-party lesson text. When the user points at a reference breakdown (for example an interview-prep site), take only its structure and facts, and write your own wording and numbers.
- Example numbers (latency, availability, scale) are labelled as example design targets, never as real product guarantees.

## 1. How a system design lesson is wired

### 1.1 The lesson object

```ts
export const myLesson: LessonContent = {
  slug: "my-lesson",                       // stable; also the progress id
  title: "Title Case Lesson Title",
  subtitle: "One short sentence, about 60 characters, no colon.",
  sections: [ /* stages 1 to 6, then takeaways, then quiz */ ],
};
```

- A subtitle that is a long sentence wraps into an awkward two-line header. Keep it short. If the supplied intro text is long, put it in the first section's `body`, not the subtitle.
- `LessonLayout` (route `src/routes/system-design/<track>/$topic/$lesson.tsx`) already provides the breadcrumb, progress bar, floating table of contents, prev/next and the completion button, and marks the lesson complete when the quiz fires `quiz-passed`. Do not rebuild any of it.

### 1.2 Registration checklist

A lesson shows up in navigation only when all of these agree. Missing one breaks the cards or the sidebar.

- [ ] **Content**: add the lesson to its topic's `lessons: [...]` array at the bottom of `src/lessons/system-design/<track>-content.ts`. `roadmap.ts` builds the sidebar from these topic objects, so the slug, title and order come from here.
- [ ] **Track index**: `src/routes/system-design/index.tsx`. Add the lesson title to the module's `modules` list so the module card lists it.
- [ ] **Section renderer**: every section kind the lesson uses must have a `case` in `src/components/system-design/SectionRenderer.tsx` and a member in the `Section` union in `src/lessons/types.ts`. Verify, do not assume.
- [ ] **Rivet index**: `src/lib/rivet/available-lessons.generated.ts` is generated by the Vite plugin on dev start. Do not edit it by hand.
- [ ] **Placeholders**: a lesson whose content is coming soon has `sections: []`, nothing else. `LessonLayout` then renders the "Lesson Content Coming Soon" state.

### 1.3 File layout

```
src/
  lessons/system-design/<track>-content.ts      # lesson content only
  lessons/types.ts                              # Section union; add lesson-owned kinds here
  components/
    system-design/
      SectionRenderer.tsx                       # one case per kind; register lesson-owned kinds
      <track>/<Name>.tsx                        # lesson-owned animation or visual
    lesson/
      SectionMarker.tsx                         # the "01 WHY" marker (shared)
      Quiz.tsx                                  # global quiz
      diagram-board/                            # global whiteboard (section 5)
    dsa/shared/PatternExercises.tsx             # shared exercise cards (section 4)
```

Reuse shared components before writing new ones. Unique visuals go in `src/components/system-design/<track>/`.

## 2. Lesson structure

Six numbered stages. Each opens with a `prose` section that has an `eyebrow` (rendered as a numbered section marker that also names the stage in the table of contents) and a descriptive `heading`:

```ts
{ kind: "prose", eyebrow: "1 · Why", heading: "Why do requirements exist?", body: ["..."] },
```

Only stage-opening sections get an eyebrow. Follow-up sections inside a stage have none.

| Stage | Eyebrow | Purpose | Typical sections |
|---|---|---|---|
| 1 | `1 · Why` | The interview or production problem this concept solves, with the one running example | `prose`, `list`, one `image` |
| 2 | `2 · Intuition` | A real-world analogy, then "now apply it to software" | `prose`, `callout`, `callout`, `prose`, `callout` (memory rule) |
| 3 | `3 · How` | The process, step by step | `prose`, the walkthrough animation, step sections |
| 4 | `4 · Example` | The concept applied to the running example | `prose`, `code`, `table`, `callout` |
| 5 | `5 · Trade-offs` | What can go wrong, costs, when not to use it | `prose`, `table`, `callout` |
| 6 | `6 · Practice` | Apply it by hand, no solutions yet | `prose`, `pattern-exercises` |

Then, **always last and in this order**:

1. `{ kind: "takeaways", items: [...] }`: 4 to 6 concrete, testable statements. Required in every lesson.
2. The optional whiteboard (`diagram-board`) goes **before** the takeaways, at the end of Practice.
3. `{ kind: "quiz", questions: [...] }`: always the very last section, after the takeaways. The completion button is added by `LessonLayout`.

Rules for every stage:

- **Image**: use the lesson infographic through the `image` kind (it uses the zoomable image component). Every `image` needs a descriptive `alt` and a `caption`. Several related images in one place use `image-carousel`, never consecutive `image` sections. Do not remove an image the lesson already has. Imports use the real file name (check the file exists before importing).
- **Callouts**: interview rules and memory aids use `tone: "info"`; failure modes and traps use `tone: "warn"`; the key takeaway of a stage uses `tone: "success"`; "not a pattern" or conceptual notes use `tone: "violet"`.
- **Tables** for comparisons and trade-offs. Give each a short `caption`. A trade-off table always has a column for the cost or failure mode, never only benefits.
- A senior-engineer framing sentence belongs in Trade-offs: requirements justify technology, technology does not justify itself.
- Stage 4 shows a small flow as text or a `code` block only if the animation does not already show it. Do not duplicate the same flow twice on the page.

## 3. The walkthrough animation (stage 3 or 4)

Every concept lesson has one lesson-owned animation, built to the same frame as the pattern lessons so the whole site feels the same. The reference is `UrlShortenerWhiteboard.tsx`. It is a hand-drawn style SVG whiteboard driven by a flat list of steps.

### 3.1 Frame (identical in every lesson)

- Outer `section`: `@container relative overflow-clip rounded-2xl border border-hairline bg-slate-50 shadow-sm`, with the two blurred corner glows, `tabIndex={0}` and an `aria-label`.
- **Window chrome**: the three traffic-light dots, a divider, a sparkle icon, a file-style name (`url_shortener.board`) and a short label. Under it, one row of **preset pills** that jump to the first step of each group (for example Requirements, Create, Redirect, Check).
- **Stage**: a fixed-height box (about `17.5rem`) with a dotted background and the SVG inside. The height never changes between steps.
- **Status card**: a numbered step badge (a check on the last step), the phase title in mint, one or two sentences of narration, and stat chips. Invisible copies of the longest narrations reserve the card height so it never resizes.
- **Transport bar**: progress line, Autoplay / Pause / Replay, previous, next, reset, `n / total`, and a 0.5x / 1x / 2x speed toggle. Left and right arrows step, space plays. Autoplay is **off** until the learner presses it. It also pauses on the `quiz-started` window event.
- No code panel. System design lessons have no Python or algorithm listing.

Until the frame is extracted into a shared component, copy the reference file's frame exactly. **When you build the second system design animation, extract the frame into a shared `LessonWalkthrough` component first** (frame, controls, status card; the lesson passes `steps` and a `Stage`) and move the reference lesson onto it, rather than creating a third copy.

### 3.2 Steps

One flat array. Each step carries what the status card and the stage need:

```ts
type Step = {
  stage: "board" | "create" | "redirect";   // which scene to draw
  group: string;                            // which preset pill it belongs to
  phase: string;                            // status-card title, sentence case
  narration: string;                        // one or two sentences: what happens and why
  stats: { label: string; value: string; tone?: "mint" | "violet" | "amber" }[];
  // plus whatever the stage reads: positions, flags, labels
};
```

- One step per meaningful moment, not per animation frame. 14 to 20 steps is typical.
- Keep the **same stat labels on every step** and show `"·"` or `0` for "not yet".
- Interviewer lines can appear in narration as `Interviewer: "..."`. Keep them short.
- Start the animation with the requirements or the question, and end with a check against the stated requirements. State plainly what the design does not yet prove.

### 3.3 Visual rules

- Colour roles are fixed: **mint** services and functional, **violet** data stores and non-functional, **amber** cache or warning, **rose** messaging, **sky** edge and networking, muted grey for clients. Reuse `TONES` from `src/components/lesson/diagram-board/tones.ts`.
- Draw boxes with a rough SVG filter (`feTurbulence` plus `feDisplacementMap`) and a draw-on stroke. **Do not apply the filter to a zero-height or zero-width line**: its bounding box is empty and the line disappears. Arrows stay unfiltered.
- A moving packet is a `g` with `animate={{ x, y }}`. **Never animate `x` or `width` on an SVG `rect`** with motion: it becomes a transform and the rect shifts. Use a plain `rect` and animate the wrapper.
- Place check marks and question marks **where the bullet was**, not at the right edge, so they never overlap the text.
- Keep chips and labels attached to what they describe. Put a packet above or below a node at the start and end of a path so it never covers a box.
- Respect `useReducedMotion`. Do not use `AnimatePresence mode="wait"` for content that changes every step.
- Size with a `viewBox` (about `760 x 320`) and `h-full w-full`, not fixed pixel widths, so it fits a laptop and a phone.

## 4. Practice exercises (stage 6)

Use the shared `pattern-exercises` section so practice looks identical to the Patterns track. See `.agents/skills/patterns-lesson-structure/SKILL.md` section 5 for the card types.

- **2 or 3 cards**, no more. Do not repeat what the quiz asks.
- Lead with a short `prose`: "Do not look for solutions yet. I want to see how you think."
- Use `choice` cards for classification (for example Functional, Non-functional, Not sure) and for "pick the measurable rewrite". Use `fields` when the answer is a number. Label cards `Practice A`, `Practice B` when the supplied text letters them.
- `hint` is the next thing to think about, never the answer. `success` says why the answer is right in one sentence.
- Never make "Not sure" the correct answer.

If the lesson has a whiteboard board (section 5), put it after the exercises with one sentence of lead-in, and say that it is optional practice.

## 5. The global whiteboard (`diagram-board`)

Any lesson can add a drawing exercise with one section:

```ts
{ kind: "diagram-board", boardId: "url-shortener-basic" }
```

Everything lives in `src/components/lesson/diagram-board/`:

| File | Owns |
|---|---|
| `rules.ts` | `BOARDS`: each board's prompt, starter shapes, example answer, pass rules, pass note. **This is the file you edit for a new lesson.** |
| `components.ts` | `SYSTEM_DESIGN_COMPONENTS`: the shared, pre-labelled component palette, grouped by role |
| `shapes.ts` | Builds Excalidraw elements (plain shapes and the grouped cylinder) |
| `tones.ts` | Colours shared by shapes and palette previews |
| `graph.ts` | Reads a drawing into labelled components and arrows for the rules |
| `ExcalidrawCanvas.tsx` | The only module that imports Excalidraw (lazy, browser only) |
| `ComponentPalette.tsx` | Grouped, searchable palette; click to add, drag to place |
| `DiagramBoard.tsx` | Chrome, goals strip, colour picker, actions, Passed badge |

### 5.1 Adding a board

1. Add a `BOARDS` entry: `id`, `file` (`name.board`), `title`, `prompt` (2 or 3 sentences), `rules`, `starter`, `solution`, `passNote`.
2. Write **structure rules, never layout rules**: `{ node: [keywords] }` and `{ edge: { from: [...], to: [...] } }`. Reuse the keyword lists (`USER`, `SERVICE`, `DATABASE`, `CACHE`) so labels such as "SQL Database" and "App Service" match without renaming.
3. The `solution` must score full marks. After building, load "Show example" and confirm the goals reach `n / n`.
4. Passing is **optional**. Never block lesson completion on it. Reset clears the Passed badge; Clear only empties the drawing; the badge reads "Passed earlier" when the current drawing no longer meets the goals. Drawings and the badge are saved in this browser only (`localStorage`).
5. Add components to `SYSTEM_DESIGN_COMPONENTS` only when a lesson needs a new building block. Group them under an existing `ComponentGroup`, or add a group and its position in `ComponentPalette`'s `GROUP_ORDER`.

### 5.2 Notation (keep consistent across lessons)

Databases are **cylinders** (one grouped component; the body keeps the component id so arrows attach). Services are rounded boxes, DNS and CDN are ellipses, the load balancer is a diamond, the cache is a square-cornered amber box, queues are rose boxes. Do not introduce new shapes for the same concept in another lesson.

### 5.3 Excalidraw pitfalls (all of these happened)

- Load it only through `React.lazy` inside `ClientOnly`, **and guard the import with `import.meta.env.SSR`** (see `DiagramBoard.tsx`). `lazy` and `ClientOnly` alone are not enough: the bundler still puts Excalidraw into the server build, next to the React code every page shares, so on Vercel every page crashed with `ReferenceError: window is not defined` and showed "This page didn't load". The build log still said success.
- Set `handleKeyboardGlobally={false}` so its shortcuts never hijack the page.
- The floating properties panel covers the canvas. It is hidden with an injected rule using `!important`, because a Tailwind utility class loses to Excalidraw's own CSS. The learner picks colours from our colour strip instead.
- The site's global `::selection` colour becomes dark on dark in Excalidraw's dark mode. The board overrides `::selection` inside `.sb-excalidraw`.
- Excalidraw measures text with whatever font is ready. **Wait for the font** (`whenFontReady()`) before building elements, and pad composite label boxes, or the last letters are clipped.
- `convertToExcalidrawElements` regenerates ids by default. Pass `{ regenerateIds: false }` whenever you group parts or position labels by id.
- Arrows are not always attached and labels are not always bound (learners type loose text, draw arrows by hand). `graph.ts` therefore also accepts loose text on or near a shape and arrows that merely start and end on or near shapes. Keep that behaviour; test it with the node script described in section 8.
- Excalidraw's Library panel is a flat grid and cannot show group headings, so the grouped palette is ours and Excalidraw's own Library button is hidden. Do not add community libraries: learners must build from our named components so boards can be graded reliably.
- **Nothing on a lesson page may take focus or scroll on load.** `autoFocus` on a button inside the board made the lesson open scrolled 22,000px down to the whiteboard. The tip popup now opens only when the canvas scrolls into view (an `IntersectionObserver` on the canvas area, not the whole card) and focuses its button with `focus({ preventScroll: true })`. Check that a lesson opened from the sidebar starts at `scrollY` 0.
- A first-visit tip popup (key `sb-diagram-tip:v1`, reopened by "How it works") asks learners to use the components. Keep its wording free of promises the checker does not keep: hand-drawn shapes can still pass, but only clearly named components are reliably recognised.

## 6. Key takeaways

- 4 to 6 items, each a concrete, testable statement a learner could check themselves against. Not a repeat of headings.
- Reuse the lesson's exact definitions so they match the Why and Intuition stages.
- Always placed immediately before the quiz.

## 7. Quiz

- **5 or 6 multiple-choice questions.** System design has no coding challenge.
- Ordered easy to hard so beginners are not discouraged and seniors still get a real question. Cover different skills, for example: a core definition, classify or spot an implementation decision, clarify an ambiguous requirement, read a metric correctly (what p95 means), and distinguish two easily confused ideas (scale versus availability).
- **Do not repeat** the practice exercises. If an exercise already asks "functional or non-functional", the quiz asks something different.
- Options are shuffled at runtime: never write "A.", "B." or "all of the above". Every question has an `explanation` that says why the right option is right and, where useful, why the tempting one is wrong.
- Wrong options must be plausible. Remove joke options.
- Placed last, after the takeaways. The pass rule and the completion event are enforced by the global `Quiz`.

## 8. Verification checklist

Run all of these before you report the lesson done.

1. `npx tsc --noEmit`, `npx eslint` on every file you touched, and `npx prettier --write` on new files. Existing lint errors in files you did not change are not yours to fix, but name them.
2. **Structure**: the table of contents lists exactly the six stage names; takeaways are second to last and the quiz is last; every `image` has a `caption`; there are no em dashes (`grep` the lesson body); no section kind is missing a renderer case.
3. **Animation**: step through every step with the next button. The stage height and the status-card height never change. No text overlaps a mark or another label. Check the last step, the first step, and every group pill.
4. **Whiteboard**:
   - "Show example" scores `n / n` and shows Passed; Reset clears the badge; Clear keeps it as "Passed earlier".
   - Test the checker with node directly (`node --experimental-strip-types`, copying `graph.ts` and `rules.ts` to a scratch folder with the Excalidraw type import replaced by `any`): fully bound, loose text on shapes, loose text beside shapes, unattached arrows, labelled shapes with no arrows (must score partial).
   - Insert components from the palette by click and by drag, search for one, and confirm the goals tick.
   - Type a label into a shape in **light and dark** mode and confirm it is readable while editing and after.
5. **Browser** (hidden panes freeze animation, so verify state through the DOM and say plainly when smoothness was not observed): at 375, 768, 1024, 1280 and 1440px there is no page-level horizontal scroll; at 1280px the animation's controls stay on screen; the whiteboard canvas and its goals strip are fully usable; no console errors. Remove any test data you wrote to `localStorage` (clear the board afterwards, because the board re-saves on change).
6. **Production (server rendering)**: a passing `npm run build` is not enough. Run `VERCEL=1 npm run build`, then call the server function and check that pages return 200 and that no browser-only library ended up in it:

   ```bash
   grep -rl "excalidraw" .vercel/output/functions/__server.func | wc -l    # expect 0
   node scratch/ssr-test.mjs "$PWD/.vercel/output/functions/__server.func/index.mjs"
   ```

   The script imports the function's default export and calls `fetch(new Request("http://localhost/<path>"))` for `/` and the lesson path, printing the status and whether the body contains "This page didn't load". Do this for any lesson that adds a browser-only dependency.

## 9. Do not

- Do not reword supplied lesson text, reorder its facts or drop its examples.
- Do not put a second copy of the animation frame in a lesson; extract the shared frame when you build the second one.
- Do not duplicate the same flow as text, an image and an animation on the same page without a reason.
- Do not make the whiteboard required for completion.
- Do not import Excalidraw anywhere except `ExcalidrawCanvas.tsx`.
- Do not write lesson-specific shapes or components into `diagram-board/`; keep lesson content in `BOARDS`.
- Do not skip the practice or the takeaways, or place the quiz anywhere except last.
- Do not use em dashes, filler, or generic AI phrasing.
- Do not change the global sidebar, Rivet, `LessonLayout` or quiz behaviour for one lesson without asking.

## 10. Shipping changes

The working folder may not be a git repository. Tell the user exactly what to move, because a partial upload breaks the build.

- **List every file**, grouped as *add*, *update* and *delete*, with a one-line reason each. For a lesson with a whiteboard that normally means:
  - the topic content file, `src/lessons/types.ts`, `src/components/system-design/SectionRenderer.tsx`, `src/routes/system-design/index.tsx` if the module list changed;
  - the lesson's animation file;
  - the whole `src/components/lesson/diagram-board/` folder, `src/components/lesson/SectionMarker.tsx` (and the Python renderer that imports it);
  - `package.json` and `package-lock.json` (the `@excalidraw/excalidraw` dependency);
  - the lesson image in `src/images/system-design/`.
- **Exclude unrelated changes** and name them.
- **Upload before deleting.** Add and update first, then delete replaced files, and say staging can be briefly broken in between.
- **Dependency licence**: `@excalidraw/excalidraw` is MIT licensed. No community libraries or third-party artwork ship with the board.
- **Back up deletions** and say where the backup lives and whether it survives the session.
- Give a **post-deploy check**: the table of contents, the animation controls, the exercises, the whiteboard (palette, example, badge, reload keeps the drawing), quiz completion, and that the other lessons in the track still load.
